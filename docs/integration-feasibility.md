## Codex CLI: supported path and limits

`codex exec --json` is the simplest V1 integration. The installed `0.157.1` help confirms `-C`, `-m`, `-c`, `--sandbox`, `--ephemeral`, `--ignore-user-config`, `--strict-config`, and `--json`. Official non-interactive documentation lists `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*`, and `error` event families. It also states that exec normally uses saved authentication and needs a Git repository. [Non-interactive mode](https://developers.openai.com/codex/noninteractive), [CLI reference](https://developers.openai.com/codex/cli/reference).

`codex login status` is a supported auth-method check. The inspected implementation prints "Logged in using ChatGPT" for ChatGPT modes, but partially masks and prints API keys in API-key mode. Agent Cost Lab captures and classifies this output without persisting or echoing it. The current local method classified as subscription; each live attempt must recheck it. API-key environment overrides and custom providers are rejected in V1. Do not inspect `auth.json` or extract bearer tokens. [Auth documentation](https://developers.openai.com/codex/auth), [login source](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/cli/src/login.rs).

Source inspection shows `turn.completed.usage` is populated from the most recent **thread total**, not a separately additive turn delta. When no usage notification has arrived, the processor's default can look like zero usage. Its public usage type includes input, cached input, cache-write input, output, and reasoning output. This is why the event parser needs version-specific accounting and ambiguous-zero handling. [Event processor](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/exec/src/event_processor_with_jsonl_output.rs), [usage type](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/exec/src/exec_events.rs).

The CLI can report observable command/file/MCP activity and terminal errors, but that does not establish the number of internal model requests, all retries, billing, or first-request token usage. Rate-limit and auth failures must stop the campaign without a silent paid fallback. Handle SIGINT, timeout, and partial JSONL as incomplete attempts. The installed exec source contains a headless default of no approval prompts; use the sandbox and restrictive permission profile rather than bypass modes. [Exec source](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/exec/src/lib.rs), [permission configuration](https://developers.openai.com/codex/config-reference).

The [Codex App Server](https://developers.openai.com/codex/app-server) exposes richer account and rate-limit methods and could be reconsidered if CLI gaps block the experiment. Its external-token mode is not needed. Replacing the CLI now would add interface and lifecycle complexity without resolving a demonstrated V1 blocker.

### Caching-only conclusion

OpenAI's Responses API documents provider prompt caching, cached-token usage, cache controls for eligible models, and response-based cache-miss diagnostics. These are API capabilities. The inspected Codex CLI reference offers no supported invocation-level control over its internal message ordering, tool list, cache breakpoints, cache keys, or diagnostics. The Codex client source internally derives cache affinity from session metadata; that does not make the derivation a supported lab intervention. [Prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching), [diagnostics guide](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics), [Codex client source](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/core/src/client.rs).

Accordingly, **`codex_cache_optimized` is unsupported/deferred for subscription V1**. No result should be labeled caching-only by compressing content, changing reasoning, changing models, switching billing mode, or simply starting another process.

## Headroom: candidate integration and hazards

Headroom `0.39.1` documents a Codex wrapper and local proxy. Inspected source contains subscription-specific routing, HTTP and WebSocket Responses handling, per-frame compression, usage extraction, and tests for later frames, streaming lifecycle, passthrough, and cleanup. The original assessment did not live-test 0.157.1. Subsequent authorized validation used installed Codex 0.160.0; [one integrated matched pair](live-validation.md) passed the specified acceptance tests but used more total resources with Headroom. [Headroom README](https://github.com/headroomlabs-ai/headroom/tree/d13e1966f820220b482a33c30bde1e926743939a), [wrapper](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/cli/wrap.py), [Responses handler](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/proxy/handlers/openai.py), [lifecycle tests](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/tests/test_openai_codex_ws_lifecycle.py).

The stock wrapper is unsuitable as the initial lab boundary: it can register MCP tools in the durable Codex configuration, choose extra navigation tooling, alter child environment verbosity, and print human status text on stdout. Its per-session routing code is useful, but the lab should run the existing proxy executable under its own process control and use invocation-local Codex overrides. Users should not manually launch the wrapper or configure retrieval. Do not run Headroom's global wrap, unwrap, persistent install, or recovery commands as part of a trial. A supported Codex `openai_base_url` override exists, but source-level routing compatibility does not equal an OpenAI guarantee that every future subscription protocol will work through a third-party proxy. [Wrapper source](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/cli/wrap.py), [Codex configuration reference](https://developers.openai.com/codex/config-reference).

### Implemented lifecycle, bounded live validation

Agent Cost Lab requires an explicitly installed, project-local pinned Headroom dependency; allocates a dedicated loopback endpoint and isolated proxy/MCP state; starts the existing Headroom proxy in an owned restricted process group; supplies invocation-local Codex routing and retrieval MCP settings; checks readiness; collects CLI usage and separate Headroom treatment observations; and shuts down owned processes and removes temporary state after success, timeout, interruption, or error. The trusted client starts retrieval in its own restricted process with an owned cwd; only the retrieval tool is exposed to the agent. The agent cannot directly read proxy originals, MCP state, or trusted verifier material. The compatibility record requires an explicit description of observed effective settings before a normal `optimize` run; `headroom-check` can collect evidence without asserting that the treatment is validated. It must not read/copy subscription tokens or alter global Codex/Headroom files. A baseline run does not require Headroom; an optimization request with no verified backend stops with a blocker, never a mislabeled baseline. Proxy/MCP readiness, restricted retrieval of a synthetic retained original, interrupted proxy cleanup and effective settings are model-free tested. One live task validates subscription routing, actual compression, later-turn execution and complete terminal CLI usage. Each assertion has the narrow evidence boundary in [live-validation.md](live-validation.md).

The candidate configuration is a dedicated loopback Headroom proxy in `cache` mode with per-run state, local metrics, beacon disabled, raw traffic logging disabled, and unrelated routing, memory, learning, output shaping, and semantic-response caching disabled. Start with model-free compression components and disable Kompress plus fallback to avoid an implicit model download. The exact installed package and flags must be validated offline before launch. A setting's presence in a config is not proof that it was effective. [Proxy options and telemetry](https://docs.headroomlabs.ai/docs/proxy).

Reversible compression can emit markers referring to locally retained originals. The wrapper registers an MCP server for `headroom_retrieve`; its canonical subprocess is `headroom mcp serve`, pointed at the proxy by `HEADROOM_PROXY_URL`. A per-run MCP registration must be present, reachable, and included in the declared treatment. `--no-mcp` is invalid if the selected compression path can emit retrieval markers. If retrieval fails or originals expire before verification, the treatment setup is invalid. [MCP registration source](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/mcp_registry/install.py), [CCR documentation](https://docs.headroomlabs.ai/docs/ccr).

Headroom's CacheAligner is **detector-only**, disabled by default, and hard-disabled in proxy traffic. It does not rewrite, repair, reorder, or compress prompts. The proxy's `cache` mode aims to retain older prefix content while compressing an eligible newest delta. That treatment changes content; it is not a caching-only fix. [Cache optimization documentation](https://docs.headroomlabs.ai/docs/cache-optimization), [detector tests](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/tests/test_cache_aligner_detector_only.py).

Headroom can bypass ineligible content, fail, or forward original content after some failures; a successful Codex run does not prove compression happened. A live gate must establish request routing through the proxy, actual modified units or an explained inapplicable result, usable retrieval, later-turn continuity, preservation of streaming/tool events and usage, and owned-process cleanup on interruption. A no-effect eligible run can be measured as zero compression. Report active with effect, active without improvement, inapplicable, unexpected bypass, integration failure, or unknown separately from external task success. An unexpected bypass or compatibility failure cannot be reported as successful optimization. Keep Headroom token estimates distinct from provider-reported usage. [Compression handler](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/proxy/handlers/openai.py), [failure policy](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/headroom/proxy/helpers.py).

Headroom source metadata declares Apache-2.0 and includes a NOTICE. Pin a supported package version that matches the inspected behavior; include required license and attribution when distributing it. [Package metadata](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/pyproject.toml), [LICENSE](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/LICENSE), [NOTICE](https://github.com/headroomlabs-ai/headroom/blob/d13e1966f820220b482a33c30bde1e926743939a/NOTICE).

## Ollama: later local adapter

The installed Codex CLI exposes `--oss --local-provider ollama`. Its source checks local Responses support and may **pull a missing model automatically**. Doctor and dry-run must never launch that path. A later local run must preflight an explicitly selected, already-installed model and refuse to start if absent. Do not substitute Codex's default `gpt-oss:20b` merely because the CLI offers one. [Codex Ollama adapter](https://github.com/openai/codex/blob/36650394c5b38c2990ccf2a3457165ca3e9d9726/codex-rs/ollama/src/lib.rs).

Ollama documents stateless OpenAI-compatible Responses with streaming and function calling, but not `previous_response_id` or conversation state. Its native chat response documents `prompt_eval_count`, `prompt_eval_cached_count`, `eval_count`, `load_duration`, `prompt_eval_duration`, `eval_duration`, and `total_duration`; their availability through Codex's Responses path has not been established. Do not assume feature parity merely from an OpenAI-compatible URL. [Compatibility](https://docs.ollama.com/api/openai-compatibility), [native chat API](https://docs.ollama.com/api/chat).

If added later, compare the **same** local model digest, quantization, context size, tools, and concurrency settings across local arms. Check that the model can solve the fixture tasks, separate load from steady-state execution, measure memory and Headroom overhead, and stay within the practical 18 GB budget. Local token changes are not OpenAI API-dollar savings.

## Future paid API mode and diagnostics

This is a separately authorized, explicit billing mode. Provider usage and a dated pricing source must cover all documented billable input categories, cached reads, cache writes, output, reasoning where billed, tools, failures, and retries. If usage is incomplete, cost is unknown. Usage-calculated estimates must not be presented as invoice-reconciled charges.

For supported Responses API models, prompt-cache diagnostics compare a current request with a prior response ID. They require response IDs and compatible settings. Neither availability nor IDs have been established in subscription `codex exec --json` events. Keep diagnostics out of V1 rather than inferring misses from local hashes. [Diagnostics documentation](https://developers.openai.com/api/docs/guides/prompt-caching/diagnostics).

## Decision and next gate

**Recommended V1 architecture:** one Agent Cost Lab `optimize` workflow that manages native subscription Codex baseline and Headroom-backed context optimization, independent verification, and local comparison reports. The offline parser, task fixture, verifier, controller, and reporting code now exist. **Caching-only:** unsupported/deferred on the inspected CLI surface. **Headroom:** the authorized pilot and supplementary probes now validate the exact-version managed path within the limits recorded in [live-validation.md](live-validation.md). The baseline now passes on this installation. The integrated matched pair now works and reports a measured regression; next, freeze controls before any separately authorized repeated campaign. No caching-only intervention or measured optimization benefit is established by the baseline.
